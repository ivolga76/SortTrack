# Тестовая медиатека для приёмки SortTrack MVP

Документ определяет безопасный минимальный набор данных для ручной приёмки. Он не разрешает изменять пользовательские оригиналы.

## 1. Наборы данных

### A. Representative media corpus

Отдельная копия 200–500 реальных треков:

- примерно поровну MP3 и FLAC;
- все основные широкие жанры текущей таксономии;
- разные значения BPM, key/Camelot, rating и полнота тегов;
- файлы с обложками и без них;
- кириллица, латиница, пробелы, скобки и допустимые специальные символы в путях;
- вложенность каталогов от 0 до 10 уровней;
- длинные, но допустимые Windows-пути;
- минимум по одному read-only, повреждённому и исчезающему во время теста файлу;
- несколько полных SHA-256 дубликатов, включая одну запись в MP3 и FLAC как разные файлы;
- конфликты одинаковых имён с одинаковым и разным содержимым.

Этот набор используется для scan, воспроизведения, waveform, плейлистов, тегов, Copy, дубликатов и экспорта.

### B. Fault corpus

20–50 дополнительных копий, которые разрешено повреждать, блокировать и менять. Набор используется только для `FI-01`–`FI-10` из протокола приёмки.

### C. Performance corpus

- существующая синтетическая база v13 на 100 000 треков используется для повторяемого SQL baseline;
- реальная или обезличенная файловая библиотека используется для измерения scan и декодирования;
- если 100 000 реальных файлов пока недоступны, отчёт обязан отдельно показать фактическое количество файлов и не выдавать синтетический SQL-тест за полный пользовательский прогон.

## 2. Рекомендуемая структура

```text
work/mvp-acceptance/
  source-readonly/
  source-writable-copies/
  fault-corpus/
  copy-destination/
  exports/
  backups/
  evidence/
  manifests/
```

Папка не должна находиться внутри пользовательской музыкальной библиотеки. Destination, exports и backups не должны находиться внутри source.

`work/mvp-acceptance` исключён из Git: локальные пути, manifests, логи и другие доказательства приёмки не должны попадать в публичный репозиторий.

## 3. Manifest до и после

До первого запуска для каждого файла фиксируются:

- относительный путь;
- размер;
- время изменения;
- полный SHA-256;
- ожидаемый формат;
- признак разрешённой записи тегов.

После каждого сценария сравнивается manifest. Любое неожиданное изменение исходного файла является P0 и немедленно останавливает приёмку.

Для создания manifest без изменения музыки:

```text
npm run acceptance:manifest -- --root <source-readonly> --output <evidence/before.json>
```

Для строгого сравнения после сценария:

```text
npm run acceptance:manifest -- --root <source-readonly> --compare <evidence/before.json>
```

Команда завершится с ненулевым кодом при добавленном, исчезнувшем или изменённом MP3/FLAC. Существующий manifest никогда не перезаписывается.

## 4. Запрещённые действия

- использовать единственную копию MP3/FLAC;
- проводить fault injection на installed-профиле с пользовательской базой;
- помещать destination внутрь source;
- подтверждать изменение тегов на read-only наборе;
- вручную удалять временные файлы до фиксации состояния восстановления;
- считать тест успешным только по сообщению UI без проверки хешей, базы и итогового отчёта.

## 5. Доказательства

Для каждого ручного теста сохраняются:

- заполненная строка `MVP_ACCEPTANCE.md`;
- скриншот результата или диалога ошибки;
- экспортированный локальный отчёт операции;
- relevant log fragment без аудиоданных и секретов;
- manifest до/после для файловых сценариев;
- характеристики компьютера и длительность для performance-тестов.
