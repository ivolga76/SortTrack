## 1. Назначение продукта

SortTrack предназначен для разбора новой электронной музыки, организации локальной музыкальной библиотеки, определения жанров и поджанров, создания плейлистов и безопасного копирования выбранных файлов в пользовательские папки.

Основной пользовательский сценарий:

1. пользователь добавляет папку с новой музыкой;
2. приложение быстро индексирует MP3 и FLAC без изменения исходных файлов;
3. пользователь прослушивает треки, проверяет метаданные и сортирует музыку;
4. приложение предлагает жанры и поджанры;
5. пользователь подтверждает один из вариантов или назначает жанр вручную;
6. пользователь формирует плейлисты;
7. приложение безопасно копирует треки в выбранную папку или раскладывает копии по шаблону;
8. пользователь получает отчет обо всех выполненных и пропущенных операциях.

SortTrack является организатором музыкальной библиотеки, а не DJ-программой, стриминговым сервисом или аудиоредактором.

## 2. Обязательные принципы

1. Добавление папки создает только логический индекс и не изменяет музыку.
2. Исходный файл изменяется только по явной команде редактирования метаданных.
3. Физическое копирование выполняется только после preview и подтверждения.
4. MVP не перемещает и не удаляет исходные аудиофайлы.
5. Ни одна операция не должна молча перезаписывать существующий файл.
6. Сбой, отмена или закрытие приложения не должны приводить к потере исходного файла.
7. Все длительные операции выполняются в фоне и не блокируют воспроизведение и интерфейс.
8. Ручная классификация пользователя имеет приоритет над автоматической.
9. Автоматический анализ предлагает варианты, но не принимает окончательное решение вместо пользователя.
10. Основные локальные функции работают без онлайн-сервисов; онлайн-обогащение является дополнительным.
11. Телеметрия не отправляется. Диагностические журналы хранятся только локально.

## 6. Хранение данных

### 6.1. Installed-версия

```text
%LOCALAPPDATA%\SortTrack\
  database\sorttrack.db
  cache\
  logs\
  backups\
  models\
  settings.json
```

### 6.2. Portable-версия

По умолчанию данные хранятся в папке `data` рядом с приложением:

```text
SortTrackPortable\
  SortTrack.exe
  data\
    database\
    cache\
    logs\
    backups\
    models\
```

Portable-версия должна явно сообщать об ошибке, если ее папка недоступна для записи.

### 6.3. SQLite

- БД хранится только на локальном диске.
- Используется WAL при поддерживаемой и протестированной версии SQLite.
- Версия SQLite закрепляется; обновления проходят regression-тесты.
- Запись сериализуется через контролируемый repository layer.
- Долгие чтения не должны удерживать транзакции без необходимости.
- Настраиваются checkpoint, `busy_timeout` и проверка целостности.
- Миграции имеют номер версии, транзакционны и тестируются на копиях реальных БД.
- Backup живой БД выполняется SQLite Backup API или `VACUUM INTO`, а не простым копированием одного файла.

## 7. Модель данных

Минимальные сущности:

### 7.1. LibraryRoot

- ID;
- canonical path;
- scan subfolders;
- exclusions;
- status;
- created/last scanned;
- volume identifier.

### 7.2. Track

Логическая музыкальная запись:

- ID;
- preferred title/artist;
- confirmed genre/subgenre;
- genre lock;
- rating;
- created/updated.

Пользовательские заметки исключены из функционального объёма по решению владельца проекта. Существующее резервное поле базы не требует интерфейса или отдельной истории.

### 7.3. TrackFile

Конкретный физический файл:

- ID и `track_id`;
- canonical path и normalized path key;
- filename/extension;
- size и mtime;
- file identity при поддержке ОС;
- SHA-256 и его статус;
- acoustic fingerprint и версия алгоритма;
- codec, duration, bitrate, sample rate, bit depth, channels;
- availability status;
- last scanned.

Автоматическое объединение нескольких TrackFile в один Track допускается только для exact duplicates. Для акустического совпадения требуется подтверждение пользователя либо отдельно утвержденный высокий порог.

- `genres`;
- `genre_aliases`;
- `genre_relations`;
- `taxonomy_versions`;
- `track_genre_candidates`;
- `audio_features`;
- `playlists`;
- `playlist_items`;
- `smart_playlist_rules`;
- `duplicate_groups`;

Все внешние идентификаторы, результаты ML и fingerprints должны содержать имя источника и версию алгоритма.

## 8. Добавление и сканирование библиотеки

### 8.1. Первый запуск

Пользователь:

1. выбирает одну или несколько папок;
2. выбирает обход подпапок;
3. настраивает исключения;
4. видит оценку количества найденных файлов;
5. запускает быстрое индексирование.

Fast является единственным режимом первоначального анализа по умолчанию.

### 8.2. Fast scan

- путь;
- размер;
- mtime;
- основные теги;
- параметры аудио;
- существующий genre tag;
- embedded cover index;
- быстрый статус доступности.

SHA-256, waveform, BPM, key, fingerprint и ML выполняются лениво или отдельными фоновыми заданиями.

### 8.3. Повторное сканирование

Обнаруживаются:

- новые файлы;
- измененные файлы;
- отсутствующие файлы;
- возможные перемещения;
- изменения метаданных вне SortTrack.

Отсутствующая запись получает статус `MISSING`, но не удаляется автоматически. Доступны «Найти файл», «Перепривязать», «Удалить из библиотеки», «Пересканировать».

### 8.4. Защита сканера

- ошибки одного файла не прерывают scan;
- циклы symlink/junction/reparse point не допускаются;
- пути нормализуются без потери исходного написания;
- исключения применяются до тяжелого анализа;
- поврежденные файлы помечаются и остаются видимыми;
- сканирование можно приостановить и отменить;
- воспроизведение имеет приоритет над анализом.

1. прочитать текущие теги, размер, mtime и контрольное состояние;

8. обновить индекс;

- удаление истории выполняется только отдельной командой пользователя.

## 14. Безопасное копирование файлов

### 14.1. Режимы MVP

- Copy Playlist Files — копирование всех файлов плейлиста в одну папку;
- Copy by Template — копирование по шаблону папок и имен;
- Move отсутствует в MVP.

Шаблон по умолчанию:

```text
{Genre}\{Subgenre}\{Artist} — {Title}.{ext}
```

Если subgenre отсутствует, пустой сегмент не создается. Недопустимые символы Windows безопасно заменяются по документированному правилу. Preview показывает каждый итоговый путь.

### 14.2. План операции

До копирования показываются:

- destination;
- число файлов;
- общий размер;
- требуемое и доступное место;
- итоговые пути;
- missing sources;
- identical destination;
- filename conflicts;
- permission errors;
- invalid names.

До подтверждения ни один файл не создается.

### 14.3. Конфликты

Конфликты показываются единым списком. Пользователь выбирает решение и может применить его ко всем конфликтам того же типа.

Типы решений:

- Skip;
- Rename Copy;
- Use Existing, только после подтвержденного одинакового SHA-256;
- Change Destination;
- Cancel Operation.

Перезапись существующего файла в MVP запрещена.

### 14.4. State machine одного файла

```text
PLANNED
→ COPYING_TO_TEMP
→ TEMP_COPIED
→ VERIFIED
→ DESTINATION_COMMITTED
→ COMPLETED
```

Ошибки:

```text
FAILED_RETRYABLE
FAILED_FINAL
CANCELLED_SAFE
RECOVERY_REQUIRED
```

Алгоритм:

1. повторно проверить источник;
2. создать уникальный временный файл в destination;
3. копировать порциями с прогрессом;
4. flush/close;
5. проверить размер и SHA-256;
6. атомарно переименовать временный файл в итоговое имя;
7. записать результат в журнал;
8. исходник не изменять.

Каждый переход состояния сохраняется до начала следующего шага. После сбоя приложение находит незавершенные операции, удаляет только собственные подтвержденные временные файлы либо предлагает восстановление.

Операция должна быть идемпотентной: повторный запуск не создает лишние копии и не меняет уже проверенный результат без решения пользователя.

### 14.5. Отчет

Для каждого файла:

- track;
- source;
- destination;
- result;
- reason;
- bytes;
- source/destination hash;
- timestamps.

Отчет сохраняется в БД и экспортируется в JSON/CSV.

## 15. Дубликаты

### 15.1. Exact Duplicate, MVP

Одинаковый SHA-256 всего файла. Hash вычисляется лениво и кэшируется по file identity, size и mtime.

### 15.2. Same Recording, версия 1.1

Акустический fingerprint используется для поиска одной записи в MP3 и FLAC. Возможные совпадения группируются, но автоматически не объединяются и не удаляются.

Разными треками по умолчанию считаются:

- radio edit;
- extended mix;
- remix;
- live version;
- remaster при обнаружимом различии;
- версия с измененным tempo/pitch.

### 15.3. Рекомендация лучшей копии

Оценка учитывает:

1. декодируемость и отсутствие ошибок;
2. lossless/lossy;
3. bit depth/sample rate без предположения, что больше всегда лучше;
4. bitrate для MP3;
5. полноту тегов;
6. наличие обложки;
7. предпочтение пользователя.

FLAC обычно получает рекомендацию выше MP3, если файл целостен. Рекомендация не выполняет удаление.

## 16. Жанры и поджанры

### 16.1. Начальная таксономия

```text
Breaks
Drum & Bass
House
Techno
 ├─ Melodic Techno
 ├─ Hard Techno
 ├─ Percussive Techno
 ├─ Peak Time Techno
 ├─ Acid Techno
 ├─ Raw Techno
 └─ Schranz

```

Нормализованные названия:

- `Breacks` → `Breaks`;
- `DnB`, `D&B`, `Drum'n'Bass` → `Drum & Bass`;
- `pictime techno` → `Peak Time Techno`;
- `Percussion Techno` → `Percussive Techno`;
- `ElectroPunk` → `Electropunk`.

Исходное значение тега сохраняется отдельно.

### 16.2. Правило единственной классификации

Пользователь выбрал модель «один итоговый жанр/поджанр».

- если выбран только широкий жанр, `genre = Techno`, `subgenre = null`;
- если выбран `Acid Techno`, `genre = Techno`, `subgenre = Acid Techno`;
- UI показывает `Techno → Acid Techno`;
- mood, energy и многожанровые назначения не входят в 1.x.

Таксономия версионируется. Пользователь может добавлять aliases, но изменение canonical taxonomy выполняется через управляемую миграцию.

## 17. Жанровый помощник, версия 1.2

### 17.1. Поведение

Для каждого трека приложение показывает три кандидата. Пользователь:

- подтверждает один;
- выбирает другой жанр;
- оставляет трек неклассифицированным;
- блокирует подтвержденный результат.

ML не записывает genre tag без отдельного подтверждения массовой записи тегов.

### 17.2. Сигналы

- существующий genre tag;
- aliases;
- структура папок и filename;
- локальная аудиомодель;
- AcoustID/MusicBrainz/Discogs в версии 1.3;
- ручная классификация.

Приоритет:

```text
locked manual
confirmed manual
verified exact external match
consistent embedded tag
local audio model
folder/filename heuristic
```

### 17.3. ML pipeline

1. декодировать аудио в mono PCM с параметрами модели;
2. исключить тишину;
3. выбрать несколько репрезентативных участков;
4. выполнить inference;
5. агрегировать результаты;
6. сопоставить labels внутренней таксономии;
7. сохранить top-3, score, model version и taxonomy version;
8. передать результат на подтверждение.

Score не называется вероятностью без калибровки.

### 17.4. Validation dataset

Использовать имеющуюся размеченную коллекцию примерно из 1000 треков.

Перед оценкой:

- проверить баланс жанров;
- выделить train/calibration/test без утечки одинаковых записей;
- зафиксировать эталонные labels;
- сохранить dataset manifest без копирования аудио в репозиторий.

Критерий выпуска:

- не менее 70% правильных широких жанров на отложенной выборке;
- публикация confusion matrix и per-class recall;
- интерфейс всегда показывает три кандидата;
- низкая уверенность не назначает жанр автоматически.

Поджанры оцениваются отдельно и не входят в порог 70% широкого жанра.

## 18. Онлайн-провайдеры, версия 1.3

- каждый провайдер отключается отдельно;
- перед включением объясняется, какие данные отправляются;
- fingerprints и metadata разрешено отправлять только после согласия пользователя;
- ключи хранятся через защищенное хранилище Windows;
- MusicBrainz использует идентифицируемый User-Agent и не более разрешенной частоты запросов;
- применяются cache, exponential backoff и jitter;
- HTTP 429/503 не считается окончательной ошибкой;
- ответ провайдера хранится с timestamp и provider version;
- онлайн-данные не перезаписывают подтвержденные пользовательские значения.

## 21. Производительность и надежность

Целевой тестовый набор: 100 000 записей MP3/FLAC на локальном SSD. Характеристики эталонного ПК фиксируются в performance report.

Цели после первичной индексации:

- запуск до отображения библиотеки: p95 ≤ 3 секунды;
- первая страница таблицы: p95 ≤ 500 мс;
- поиск FTS: p95 ≤ 250 мс;
- простой фильтр/сортировка: p95 ≤ 350 мс;
- прокрутка: без заметных зависаний, целевой уровень 50–60 FPS;
- UI action acknowledgement: ≤ 100 мс;
- начало отмены фоновой задачи: ≤ 2 секунд;
- базовое потребление RAM без анализа: целевое ≤ 350 МБ.

Fast scan должен показывать реальную скорость, прогресс и оставшееся время, но фиксированное время полного сканирования не является критерием без определения диска и файлов.

## 22. Безопасность

- минимальные Tauri capabilities;
- CSP без удаленного исполняемого кода;
- строгая валидация всех IPC-команд;
- canonicalization и повторная проверка пути непосредственно перед записью;
- запрет записи за пределы подтвержденного destination;
- sidecar-команды не принимают произвольную shell-строку;
- подпись manifest обновлений обязательна;
- ключи API не выводятся в лог;
- аудиофайлы, пути и метаданные не отправляются как telemetry;
- diagnostic bundle создается только по команде пользователя и имеет preview;
- dependency/SBOM/license scan выполняется в CI.

## 23. Логи и диагностика

- структурированные локальные логи;
- ротация по размеру и сроку;
- уровни error/warn/info/debug;

## 24. Резервное копирование и восстановление

Backup включает:

- SQLite snapshot;
- настройки;
- плейлисты;
- историю метаданных;
- ручные и заблокированные жанры;
- пользовательские aliases;
- manifest версий.

Аудиофайлы и пересоздаваемый waveform-кэш в backup не входят.

Восстановление:

1. проверить manifest и checksum;
2. проверить совместимость версии схемы;
3. сделать safety backup текущей БД;
4. восстановить во временное расположение;
5. выполнить integrity check;
6. атомарно переключить активную БД;
7. пересканировать пути без изменения аудиофайлов.

- application terminated during write;
- SQLite busy/corruption recovery;
- malformed external API response;
- network timeout/429/503.

## 27. Критерии приемки MVP 1.0

MVP принят, если:

1. индексирует тестовую библиотеку до 100 000 записей без загрузки всех строк в UI;
2. повторно обнаруживает новые, измененные и отсутствующие файлы;
3. не изменяет файлы при добавлении папки;
4. воспроизводит MP3/FLAC и показывает кэшированный waveform;
5. показывает BPM, key и Camelot либо понятный статус отсутствия анализа;
6. выполняет поиск, фильтрацию и сортировку в заданных пределах;
7. создает и сохраняет несколько ручных плейлистов;
8. DnD не выполняет физических операций;
9. массово редактирует теги только после preview;
10. обнаруживает внешнее изменение перед Undo;
11. экспортирует валидный M3U8 и Traktor NML для поддерживаемого target profile;
12. показывает полный план Copy;
13. позволяет применить решение ко всем конфликтам одного типа;
14. никогда не перезаписывает destination;
15. проверяет каждую созданную копию;
16. восстанавливается после принудительного завершения Copy без потери исходника;
17. находит exact duplicates по SHA-256;
18. создает и восстанавливает backup;
19. installed и portable версии не смешивают свои данные;
20. не отправляет telemetry и секреты;
21. проходит автоматические тесты и публикуется с SBOM, лицензиями и checksums.

Блокирующими дефектами являются:

- потеря или молчаливое изменение исходного файла;
- молчаливая перезапись destination;
- повреждение тегов без восстановления;
- потеря плейлистов/ручной классификации при миграции;
- выполнение записи за пределами выбранной папки;
- утечка ключа API;
- неподтвержденная автоматическая запись ML-жанра.

## 28. Не входит в версию 1.x

- облачная синхронизация;
- многопользовательская работа;
- мобильное приложение;
- стриминговые каталоги;
- DRM;
- автоматическое удаление дубликатов;
- изменение аудиоданных;
- beatgrid и cue editor;
- mood/energy classification;
- многожанровая классификация;
- автоматическое обучение модели на устройстве;
- прямое изменение базы Traktor;
- Serato и Rekordbox export;
- сетевые библиотеки/NAS как гарантированно поддерживаемый сценарий.

Любое расширение за эти границы оформляется отдельным изменением требований с оценкой безопасности, лицензий, миграций и обратной совместимости.

## 29. Порядок начала разработки

До реализации полного MVP выполнить четыре технических прототипа:

1. сканирование 10 000 файлов и UI-таблица с виртуализацией;
2. безопасный metadata round-trip на наборе MP3/FLAC;
3. Copy state machine с fault injection и recovery;
4. Traktor NML export и импорт в целевую версию Traktor.

После прототипов зафиксировать ADR:

- библиотека SQLite и режим соединений;
- metadata library;
- способ поставки FFmpeg;
- формат waveform cache;
- поддерживаемая версия Traktor/NML;
- политика лицензирования ML-моделей;
- установленный и portable update flow.

Разработка MVP начинается только после успешной проверки прототипа безопасного копирования, поскольку надежность файловых операций является главным приоритетом продукта.
